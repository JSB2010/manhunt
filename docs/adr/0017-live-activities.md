# ADR 0017 — Live Activities: the round on the Lock Screen and in the Dynamic Island

**Status:** accepted · **Spec:** §7 (outdoors-readable clocks, obvious phase labels), §10.2 (sanitized per-user state), §14 (push is supplementary, never coordinates) · **Related:** ADR 0010, 0011, 0016

**Context.** During a round the phone spends most of its time locked in a pocket or mounted in a car. The answers people need at a glance — what phase it is, how long is left, when the next ping goes out — were only on the game screen, and local deadline notifications stood in for them. Apple's Live Activities are made for this: an event with a defined start and end, under eight hours, with frequent updates. Apple documentation read for this work (October 2026): HIG › Live Activities (updated 13 October 2026 with limited-width guidance), *Displaying live data with Live Activities*, *Starting and updating Live Activities with ActivityKit push notifications*, *Creating custom views for Live Activities*, *Launching your app from a Live Activity*, ActivityKit updates, and the API pages for every call used. Firebase: *Send Live Activity updates* through FCM HTTP v1.

**Decision.**
1. **One activity per round, per phone that plays it.** It starts at the round start and ends with the round. Nights aren't one activity: nothing is live between rounds, and the HIG asks for a defined beginning and end.
2. **Content comes from the phone's own sanitized view.** `views.ts` renders `liveActivityState(roundView, clockOffsetMs)` from the `RoundView` already rendered for that phone. It holds only the phase, clock anchors, the next ping index and time, the latest ping slot's index, time and whether it had a fix, which crew has a claim under review, and the outcome with crew credit. It never holds coordinates, phone ids, rosters, photo paths or free-text reasons. A Live Activity can be read by anyone standing next to a locked phone (HIG: avoid sensitive information), so it shows less than the game screen. `liveActivityAttributes` adds the static part: round, role and crew name.
3. **The system runs the clocks.** Times are epoch seconds on the phone's clock: the server adds the clock offset the phone reported when it registered. Views use `Text(timerInterval:)`, so timers keep running without updates. Updates happen only on real transitions, such as chase start, a ping, a claim, a pause or the end. `staleDate` is the next expected update plus 90 s, and stale content says "Open the app for the latest" instead of guessing.
4. **App and server render the same thing.** The app updates the activity from every applied server view, and only when the content changed. The server sends ActivityKit pushes so the activity stays current while the app is suspended. Both use one mapping. `shared/fixtures/live-activity.json` is generated from real rendered views by `backend/tests/unit/liveActivity.contract.test.ts` and checked by `ManhuntCrewsTests/LiveActivityTests.swift`, so a local update and a push for the same view are identical and never fight.
5. **Pushes go through FCM** (`apns.live_activity_token`), using the project's existing APNs key. There's no new credential or service. After each committed round change:
   - When a round starts, phones other than the one that started it get a push-to-start. That needs iOS 17.2+, and the app must be off the foreground, where ActivityKit can't start activities. The push carries `input-push-token: 1`, so the new activity gets an update token.
   - On every round version newer than the last one sent, each registered activity gets an update. The newest version wins through a Firestore precondition, and unchanged content is skipped.
   - When the round ends, activities get an `end` with the final state and a dismissal 15 minutes later (HIG: 15–30 minutes).
   - Revoking the night ends every activity at once.
6. **When APNs refuses the credentials.** On 2026-10-22 every activity push failed with `messaging/third-party-auth-error`, one after another on every round change. A credentials rejection now pauses activity pushes for 10 minutes per instance and logs once, at error level, what to check: the APNs credentials in Firebase › Project settings › Cloud Messaging (FCM's code means APNs found them invalid or missing; push-to-start needs a token-based `.p8` key with the app's Key ID and Team ID). Registrations keep their last sent version, so activities catch up once pushes work. Alerts that didn't ride on an activity go out as regular pushes, as before.

7. **Alerts aren't sent twice.** The round's own notification for a moment (for example chase start, ping released, claim submitted, catch confirmed, safety pause, round over) rides on the activity update as its alert, with `apns-priority` 10. A device whose activity got the alert doesn't also get the regular push (HIG: don't use push notifications alongside a Live Activity for the same update). Updates without an alert use priority 5, which doesn't count against the push budget. Requests that need an answer in the app (pause request, resume vote, next round) stay regular notifications. Local deadline nudges are skipped while a registered activity carries the alerts. `NSSupportsLiveActivitiesFrequentUpdates` is set because pings can be a minute apart.
8. **Native presentations.**
   - Lock Screen: the phase banner in brief (role symbol in crew colour, phase and role words, crew and round, big rounded clock, next ping or claim deadline as a live countdown), with 14 pt margins and the system background so it fits a personalised Lock Screen.
   - Dynamic Island compact: the role symbol leading and the countdown trailing.
   - Minimal: the countdown, as the Timer app does, or the symbol when nothing counts down.
   - Expanded: role, round, phase, big clock and status line.
   - Limited width (iOS 27 `isDynamicIslandLimitedInWidth`): one 28 pt leading view and an empty trailing view.
   - `.small` family for the Apple Watch Smart Stack and CarPlay, with no controls; seekers watch it from a car.
   - `.medium` family for StandBy, with a larger clock.
   - The keyline is tinted with the crew colour. Colour means crew, never role.
   - There are no buttons. Tapping anywhere opens the night's game screen (`manhuntcrews://round?session=…`), where a catch is reviewed on the photo.
9. **People stay in control.** Settings has **Show Rounds on Lock Screen**. Turning it off ends running activities and withdraws the push-to-start token. The game screen's Options menu has **Hide Live Activity** for the current round. An activity removed from the Lock Screen isn't restarted for that round, and its token is unregistered. The iOS setting is respected and observed.

**API.** `PUT/DELETE /v1/sessions/{id}/rounds/{rid}/live-activity/{deviceId}` registers or removes the activity's push token and clock offset. The phone must play the round, and the round must be in progress. `POST /v1/devices/live-activity-token` sets the push-to-start token, or null when the phone turns them off. Bodies are strict. Registrations live in server-only `sessions/{sid}/liveActivities/{uid}_{deviceId}` docs with a 12-hour TTL. Delete-my-data, account deletion and revoke remove them.

**Consequences.**
- On a locked phone, a pocketed hider sees the next ping counting down, and a seeker in a car sees the chase clock on CarPlay or the Watch without opening the app.
- Privacy is unchanged by construction: the only input is the phone's own view. A unit test checks every phase, both roles and several phones for coordinates, ids, names and free text. A security test checks every push a host-seeker's activity received in a played round.
- Builds without push (free Personal Team, `MH_ENABLE_PUSH = NO`) still get the activity. The app starts and updates it while it runs (tracking keeps it running in the background), and local nudges remain the alert path.
- A new extension target, `ManhuntCrewsWidgets` (`<bundle-id>.widgets`), needs its own App Store provisioning profile for Prod. `scripts/ios-signing.sh install` takes it as a third argument, and `ios-release.sh` maps it in the export options.
- The app builds only with the iOS 27 SDK (the limited-width API), which the project already requires. The deployment target stays iOS 18 (`supplementalActivityFamilies`). Push-to-start needs iOS 17.2+ and is gated.
